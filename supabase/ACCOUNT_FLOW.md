# 账号绑定与数据恢复实施说明

当前 HTML 原型仍只演示交互。原生 iOS/iPadOS 版已使用 Supabase Auth、Postgres 和私有 Storage 实现以下核心流程。

## 认证方式

- App 只提供 iOS 原生“通过 Apple 登录”，通过安全 nonce 将 Apple identity token 交换为 Supabase 会话，并使用 Keychain 恢复会话。
- 不提供邮箱/密码表单、找回密码或其他第三方登录入口。
- 客户端只配置 Supabase 项目 URL 和 publishable key。严禁将 `service_role` 或其他高权限密钥放进 App。
- Apple 首次授权时可能返回姓名和真实或中转邮箱；稳定身份由 Supabase `auth.users.id` 表示。

## 首次注册并绑定本机数据

1. 用户完成认证并取得稳定的 `auth.users.id`。
2. App 保留本地数据，并为每条修改记录独立更新时间；网络不可用时继续写入本地队列。
3. 旧版本或未登录状态没有有效云端会话时，App 保留本机主养宠物；首次 Apple 登录后先把这些主养数据绑定到该 Apple 身份。旧的共同饲养缓存不会被错误转成主饲养数据。
4. 创建或更新 `profiles`；由客户端生成 UUID，将宠物写入 `pets`。首次创建宠物的账号成为主饲养员，并由数据库生成唯一八位分享码。
5. 按宠物 UUID 写入驱虫、疫苗、主粮、口味和洗澡记录。
6. 将照片压缩后上传到私有 `pet-media/<user_id>/<pet_id>/...` 路径，再保存对象路径；成员通过 RLS 访问自己已加入宠物的照片。
7. 拉取并核对宠物、记录和照片；全部成功后写入 `migration_completed_at` 和 `last_synced_at`。本地数据继续作为离线缓存，不因上传成功而删除。

写入必须可重试且幂等：客户端预先生成记录 UUID，网络中断后用同一个 UUID 重试，避免产生重复记录。

## 重装或更换设备后恢复

1. 用户登录同一账号。
2. 先显示正常界面和本地缓存，再在后台静默拉取用户拥有或已加入的 `pets`、五类记录及删除标记，不展示同步页面、进度或状态。
3. 照片保存在私有 bucket，通过登录会话受控下载，不把 bucket 改成公开。
4. 本机新增或修改后进行可重试的 UUID 幂等 upsert；同一条记录按 `updated_at` 选择较新版本，删除使用墓碑防止离线旧副本复活。
5. 更新 `last_synced_at`；同步失败保留本地缓存并允许后续重试。

## 共同饲养权限

- `pet_members` 保存成员关系；`owner` 是首次创建者，`caregiver` 是通过分享码加入者。
- 主饲养员可编辑宠物档案、查看或重置分享码、查看和移除成员，并维护全部记录。
- 共同饲养员不显示分享码，不能修改档案或二次分享；可以新增、编辑、删除记录，并可主动退出。
- 分享码由数据库随机生成并受唯一约束保护。重置后旧码立即失效，现有成员关系保持不变。
- 所有宠物与记录查询均由成员关系 RLS 控制；不能依赖客户端隐藏按钮作为权限边界。

## 数据安全与上线必做

- 所有 `public` 表开启 RLS，并使用所有权或 `pet_members` 成员关系限制访问；照片策略同样按宠物成员关系授权。
- App 已提供退出登录和“删除账号及数据”入口；生产环境已部署 JWT 校验的 `delete-account` Edge Function，并实现 Apple token 撤销流程。
- Apple Developer entitlement 与 Supabase Auth 的 Apple Provider 已为 `com.anto.PawprintDiary` 启用。
- 上传和恢复失败时保留本地记录并在下一次启动、回到前台或保存后静默重试；不展示同步状态，也不显示虚假的成功结果。
- 当前项目已部署共享表、逐操作 RLS、私有照片策略、外键索引、五类记录的逐记录冲突处理和删除墓碑；数据库级双身份测试已通过。正式提交前仍需在 TestFlight 用两个真实 Apple 测试账号完成跨设备和账号删除验收。
